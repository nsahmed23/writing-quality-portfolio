Node 24 itself doesn't have a mechanism that produces EADDRINUSE. That error comes from the OS rejecting a `bind()` call because something is already listening on 8080 when the new process starts; it's not a language or runtime-version behavior. The upgrade happening the same week the errors started is a timing correlation, not proof of causation. The far more likely explanation is that the upgrade disturbed your nodemon restart cycle, not Node's TCP stack.

Here's the mechanism that almost certainly applies to your setup. With `npm run dev` running nodemon plus ts-node, every file-triggered restart works like this: nodemon signals the running child to stop, waits for it to exit, then spawns a new one. On Windows there's no real POSIX signal delivery; nodemon and Node both simulate a handful of signals, and the actual process tree is usually nodemon, then a shell, then ts-node's `node.exe`. Nodemon relies on the `tree-kill` package to bring down that whole tree, and Windows is exactly where that kill has historically been least reliable, especially with an intermediate shell or ts-node child in the way. If the old `node.exe` doesn't actually die, it keeps port 8080 bound, and the new instance nodemon spawns collides with it. This also explains why it happens on every restart: the first `npm run dev` from a clean slate works because nothing is on 8080 yet, and each subsequent restart fails because the previous instance is still alive in the background.

Node 24 does bundle a newer npm (11.x), and it's possible something in how that version spawns `run` scripts on Windows shifted the process tree enough to tip this from occasional to every time. I don't have a confirmed, specific change to point to for that, so treat it as a low-confidence secondary theory, not an established cause. I'm also not aware of a documented Node 24 change to `listen()`/`bind()` defaults, but I can't check the live changelog or issue tracker from here, so I can't fully rule that out either. It's a much less likely explanation than the orphaned-process pattern above.

The steps below will tell you which of these is actually happening instead of guessing further.

1. Find out what currently holds port 8080 before changing anything. In PowerShell: `Get-Process -Id (Get-NetTCPConnection -LocalPort 8080).OwningProcess`. From cmd or Git Bash: `netstat -ano | findstr :8080`, then `tasklist /FI "PID eq <pid>"` with the PID from that output. If it's a `node.exe` you don't recognize as your current terminal, that confirms the orphaned-instance theory.
2. Kill it with `taskkill /PID <pid> /F` and start `npm run dev` fresh. If it comes up clean but EADDRINUSE reappears only after the next file-triggered restart, that confirms a restart/kill problem rather than a one-time fluke.
3. Compare `node -v` and `npm -v` now against what you had before Thursday, and open `package.json` plus any `nodemon.json` to see the exact `dev` script and whether nodemon has a custom `exec` or `signal` setting.
4. Check `server.ts` for shutdown handling. If there's no explicit `process.on('SIGTERM', ...)` or `process.on('SIGINT', ...)` that calls `server.close()`, the process is relying on default exit behavior, which is more fragile in a multi-process restart on Windows.
5. If steps 1 through 4 point to an orphaned process rather than a code bug, the fix is restart hygiene rather than chasing Node 24: add explicit shutdown handling that closes the server before the process exits, or replace nodemon plus ts-node with `tsx watch src/server.ts`, which owns its own restart lifecycle and drops the separate ts-node child process that Windows kill signals struggle to reach.

If step 1 turns up something that isn't Node at all, the Node 24 upgrade is coincidental, and the fix is just freeing port 8080 or moving the dev server to a different one.
