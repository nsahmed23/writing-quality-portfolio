Running out of file descriptors causes `EMFILE` because on Linux every open file, socket, and pipe your process holds counts against one number: the per-process descriptor limit (`RLIMIT_NOFILE`, what `ulimit -n` reports). When Fastify or Node tries to create one more of any of these, accepting a new connection, opening a file, connecting out to a database or another service, and the process is already at that ceiling, the kernel refuses the underlying syscall and returns `EMFILE`. Node passes that straight up as the error you're seeing. None of this is Fastify-specific; it's a kernel limit that Express, raw `http`, or any other Node server would hit the same way.

The detail that matters most is the timing: it runs fine for about six hours under load, then dies. If the limit were simply too low for your peak concurrency, you'd hit `EMFILE` almost immediately once load arrived, not six hours in. A slow climb to the ceiling is the signature of a leak: something in the request path is opening a descriptor and not releasing it, at a rate small enough per request that it takes hours of sustained traffic to add up. Raising the limit will buy more runway, but by itself it only delays the same crash.

**Why the whole process dies, not just the request.** That depends on where the `EMFILE` gets thrown relative to your error handling. Fastify normally catches errors inside a route and turns them into a 500 without taking the process down. An uncaught synchronous exception, or (as of Node 15+) an unhandled promise rejection with no `try`/`catch`, terminates the whole process by default. So if the entire server is exiting rather than individual requests failing, the `EMFILE` is probably happening outside a request's error boundary: in the server's own `accept()` on new connections, in a background interval or scheduled job, or in a fire-and-forget async call inside a handler that isn't awaited or wrapped. Check whether you have a top-level `uncaughtException` or `unhandledRejection` handler and what it logs right before exit; that will usually point straight at the code path.

**Where the descriptors are going.** Since nginx sits in front, it terminates the real client connections itself and either reuses a small pool of connections to your Fastify process or opens a fresh one per request and closes it, depending on whether the `upstream` block has `keepalive` configured. So a flood of raw client sockets piling up on the Node side is less likely; the leak is more likely in your app or its dependencies not releasing what they open. Common culprits, roughly in order of how often this turns out to be the cause:

- A database connection pool (`pg`, `mysql2`, Prisma, Knex, etc.) where a client is checked out and never released on some code path, often an error path that skips a `finally`.
- Outbound HTTP calls to another service or API where the response body isn't fully consumed, or the request isn't destroyed on error or timeout, leaving the socket half-open.
- Sockets stuck in `CLOSE_WAIT`: the remote end closed, but your process never called `close()` on its side, so the fd is never freed. This is the single most common shape of this bug.
- File streams (`fs.createReadStream`, log write streams, multipart upload handling) opened but not closed on an error or early-return path.
- A keep-alive `http.Agent`/`https.Agent` for outbound requests with no bound on `maxSockets`/`maxFreeSockets`, accumulating idle sockets instead of capping and reusing them.

**Confirming which one, rather than guessing.** I don't have access to your code, nginx config, or the running process, so these are the checks I'd run myself, in order:

- `cat /proc/<pid>/limits`, to see the actual current ceiling ("Max open files") for the running process. Don't trust `ulimit -n` in a fresh shell; it may not match what systemd, pm2, or Docker actually handed the process.
- `ls /proc/<pid>/fd | wc -l`, sampled every few minutes. If it climbs steadily under load and never drops back between requests, that confirms a leak rather than a legitimately busy server.
- `ls -l /proc/<pid>/fd`, to see what the descriptors actually are: `socket:[...]` entries versus regular file paths versus pipes. That tells you network versus file before you guess.
- `ss -tnp state close-wait`, to list TCP sockets stuck in `CLOSE_WAIT` with the owning PID. If your Node process shows up here with a growing count, that's the leak.
- To compress the six-hour feedback loop, drive one endpoint at a time with something like `autocannon` or `k6` while watching the fd count. Whichever endpoint makes it climb tells you the code path, in minutes instead of hours.

One more thing worth checking directly in your logs: the full Node error message names the syscall that failed, for example `EMFILE: too many open files, open '...'` or `..., accept`. That tells you what the process happened to be doing at the instant it hit the ceiling, not necessarily what caused the ceiling to be hit. An innocent `fs.open()` in logging code can be the thing that throws even though a leaking DB pool is the real cause, so don't anchor on whatever line the crash log points to before checking the fd breakdown above.

**Fixing it.** Close the actual leak first; that's the real fix, and the checks above will show you where it is. Raising the descriptor limit afterward is reasonable defense-in-depth, but only after the leak is closed, since otherwise you're just giving it a bigger hole to fall into. How you raise it depends on how the process runs: for a systemd unit, set `LimitNOFILE=65535` under `[Service]`, then `systemctl daemon-reload` and restart; editing `/etc/security/limits.conf` alone won't affect it, since that only applies to PAM login sessions. For Docker, pass `--ulimit nofile=65536:65536` on `docker run` or the equivalent `ulimits` key in Compose. For pm2, set the limit on whatever process (typically a systemd unit) starts the pm2 daemon itself, since pm2-managed processes inherit pm2's limits rather than a one-off shell's. Whatever you change, confirm it took effect against the actual running PID via `/proc/<pid>/limits`, not by trusting the config file. Finally, once this is fixed, put the fd count behind a periodic check or metric so a future leak trips an alert well before six hours instead of taking the process down first.

I can't verify any of this against your actual app, nginx config, or process manager, since I don't have access to either. The mechanism above (per-process fd ceiling, slow climb implying a leak, the process-death distinction) is certain; which specific thing in your stack is leaking is not, and the `/proc` and `ss` checks will tell you that directly.
