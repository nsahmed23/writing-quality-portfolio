Check the current ceiling first: `cat /proc/<pid>/limits | grep "Max open files"` (swap in your Fastify process's PID). Hitting that ceiling and getting EMFILE are not two events in a chain, cause and then effect: they are the same event described twice. Every process gets a kernel-enforced cap on open file descriptors (`RLIMIT_NOFILE`, the number `ulimit -n` shows you). When your code does something that needs a new one, accepting a connection, opening a file, connecting to a database, and the process is already at that cap, the kernel refuses the request and reports EMFILE, the standard Unix error code meaning the process has hit its file descriptor limit, instead of handing back a handle. Node's I/O layer (libuv) turns that refusal into the JS exception you're seeing. (A system-wide table filling up shows a different code, ENFILE, so that's not what you're hitting.)

The six-hour timing under load is the useful signal. A cap that's genuinely too low for your peak concurrency fails near the start of a traffic spike, not five or six hours into steady load. A slow, steady climb to the ceiling over hours is the signature of a leak: something is acquiring descriptors faster than it releases them, so the open count climbs with traffic until it hits the ceiling. Fastify itself is very unlikely to leak descriptors in normal operation, so look at application code or a dependency first, not the framework. One thing is already narrowed down: `Error: EMFILE: too many open files` is Node's own error format, which confirms this is happening in your Fastify process, not in nginx (nginx logs a differently formatted line if it hits its own limit).

**Likely leak sources**, ranked by how often this exact pattern turns out to be the cause:

1. A database or Redis client pulled from a pool and never released on an error path, for example `pool.connect()` without a matching `.release()` inside a `finally`. This matches your symptom precisely: it leaks one descriptor per request that hits the buggy branch, so the climb tracks traffic volume.
2. An outbound HTTP client, calls you make to another service or API, built without connection reuse, so every call opens a fresh socket that never gets recycled into a keep-alive pool.
3. File or upload streams (`fs.createReadStream`, multipart upload handling) that don't get closed when a request errors out or the client disconnects mid-transfer.
4. WebSocket or server-sent-event connections whose underlying socket never gets released on an abnormal client disconnect.
5. nginx not reusing keep-alive connections to your Fastify upstream (missing `keepalive` in the upstream block, or missing `proxy_http_version 1.1` with `proxy_set_header Connection ""`), which multiplies whichever of the above is already happening.

**Diagnose it before changing anything:**

1. Find the PID (under a minute): `systemctl status <your-unit>`, or `pm2 list`, or `pgrep -f node`.
2. Log the descriptor count over time instead of watching a terminal for six hours: `nohup bash -c 'while true; do echo "$(date +%T) $(ls /proc/<pid>/fd | wc -l)"; sleep 300; done' > fd-growth.log 2>&1 &`. The `nohup` matters: without it, the loop dies if your SSH session drops. Check back in an hour or two; flat means it's not a leak, a steady climb confirms one.
3. Once it's climbing, break down what's piling up: `for fd in /proc/<pid>/fd/*; do readlink "$fd"; done | sed -E 's/:\[[0-9]+\]/:[N]/' | sort | uniq -c | sort -rn`. Mostly `socket:[N]` entries point at a leaking client or connection (pool, outbound HTTP, or websocket); mostly regular file paths point at unclosed streams.
4. If sockets dominate, `sudo ss -tnp | grep <pid>` shows the remote address each one connects to, telling you whether they're piling up against your database, an external API, or nginx.

**Stopgap versus the actual fix:** raising the ceiling delays the crash but doesn't stop the leak; the count still climbs, just against a higher ceiling. If the app runs under systemd, `sudo systemctl edit <your-unit>`, add `LimitNOFILE=65536` under `[Service]`, then `sudo systemctl daemon-reload` and restart. Editing `/etc/security/limits.conf` or running `ulimit -n` in your shell won't touch this: those only affect PAM login sessions, not systemd-managed services. If it runs under PM2 instead, PM2 inherits whatever ulimit the launching shell had unless you override it; under Docker, set `--ulimit nofile=65536:65536` on `docker run` or the equivalent in your compose file. Either way, treat this as something you do alongside the diagnostics above, not instead of them.

The ranked list is inference from the stack you described and the six-hour symptom pattern, not a confirmed diagnosis.
