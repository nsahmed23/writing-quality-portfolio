Node 24 almost certainly isn't the direct cause here. EADDRINUSE just means the operating system told Node "something is already bound to port 8080" at the moment your `.listen()` call ran; it's a port-conflict signal from Windows, not a bug in the Node runtime. Starting right after you upgraded last Thursday is a timing correlation, not proof the upgrade caused it. Far more likely: a previous instance of your server is still alive and holding port 8080 when the next one tries to start.

The pattern that best fits "fails on every restart," specifically, with nodemon plus ts-node on Windows is a leftover process. On each restart, nodemon has to kill the old child process and spawn a new one. On Windows that kill step relies on emulated signal handling rather than native POSIX signals, and it's a long-standing, widely reported nodemon pain point: the old child sometimes survives the restart, so the new process collides with it on port 8080. It's also plausible that when you upgraded Node last Thursday, you closed the terminal or editor tab that had `npm run dev` running instead of stopping it with Ctrl+C, which can orphan the child `node.exe`. If that happened, it may have been sitting on port 8080 ever since, with every later restart failing against that same leftover process, or adding another one to the pile.

Confirm which is happening before changing anything:

1. Find what's holding the port: `netstat -ano | findstr :8080` (PowerShell equivalent: `Get-NetTCPConnection -LocalPort 8080 -State Listen`). The last column of the netstat output is the PID.
2. Identify that PID: `tasklist /FI "PID eq <pid>"`. If it's `node.exe`, that supports the leftover-process explanation. If it's something else, this has nothing to do with nodemon or Node 24: last Thursday is just a coincidence, and something unrelated started claiming 8080 around then.
3. Check for a pile-up: `tasklist | findstr node`. More `node.exe` entries than dev sessions you actually started means something is leaking processes on every restart instead of killing them.
4. Kill it and retry: `taskkill /PID <pid> /F`, then `npm run dev` again.

If that clears it once but EADDRINUSE comes back on the very next file-triggered restart, the fix is nodemon's kill behavior, not the port itself. Add `"signal": "SIGKILL"` to your nodemon config (a `nodemon.json` file, or a `"nodemonConfig"` block in `package.json`), or pass `--signal SIGKILL` in the dev script, so it force-terminates the old child instead of relying on the default signal that's known to be unreliable on Windows.

Worth a direct look at both.

One more thirty-second check: run `node -v` inside the actual project terminal, not a fresh shell, to confirm it's really resolving to 24.x there and not an older version some other tool is still picking up. Also check how old your installed `nodemon` and `ts-node` are; tooling that predates a new Node major version is a common source of exactly this kind of flaky restart behavior, and bumping both is low-risk.
