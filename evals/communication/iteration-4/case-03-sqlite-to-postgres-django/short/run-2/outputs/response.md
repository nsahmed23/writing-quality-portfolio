Here is the whole migration. The safe path for a dev database is Django's own `dumpdata` into `loaddata`, not a raw SQLite-to-Postgres file copy: the data round-trips through the ORM, so it lands in a schema Django itself built, and SQLite's loose typing gets caught at load time instead of silently corrupting a column.

One ordering rule matters more than anything else below: **dump the data before you change `settings.py`.** Once `DATABASES` points at Postgres, `dumpdata` reads the empty Postgres database and you get a 2-byte file.

## 1. Install the Postgres driver

```bash
pip install "psycopg[binary]"     # Django 4.2 and newer
# pip install psycopg2-binary     # Django 4.1 and older
```

Add whichever you installed to `requirements.txt` or `pyproject.toml` now, while you remember.

## 2. Dump the SQLite data (settings still pointing at SQLite)

```bash
python manage.py dumpdata \
  --natural-foreign \
  --exclude contenttypes \
  --exclude auth.permission \
  --exclude admin.logentry \
  --exclude sessions.session \
  --indent 2 \
  -o dump.json
```

What each piece is doing:

- `--natural-foreign` serializes foreign keys to content types and permissions as `["app_label", "model"]` instead of integer IDs. That is what lets you exclude those two tables and still have generic relations, group membership, and per-user permissions reconnect on the far side.
- `contenttypes` and `auth.permission` are regenerated by `migrate` on the new database. Loading them as well produces duplicate-key errors.
- `admin.logentry` and `sessions.session` are dev noise. Keep `admin.logentry` if you actually want the admin history; it resolves through natural keys fine.
- `-o dump.json` rather than `> dump.json`. Shell redirection re-encodes through the console codepage and mangles non-ASCII text, which bites hardest on Windows.

A note on a flag you will see in most copy-paste recipes: `--natural-primary` also appears there, and it changes behavior in a way people rarely notice. It omits the primary key of any object whose model defines `natural_key()`, and `AbstractBaseUser` does define one (returning the username). So adding it means your users and groups get **new** integer IDs on load. Foreign keys still resolve, because `--natural-foreign` rewrites them by username, but any user ID you have hard-coded in a fixture, a bookmark, an external system, or a plain integer column will now point at the wrong person. Leave `--natural-primary` off unless you specifically want PKs reassigned.

## 3. Record row counts before you switch

```bash
python manage.py shell -c "from django.apps import apps; [print(m._meta.label, m.objects.count()) for m in apps.get_models()]"
```

Save that output somewhere. It is the only thing that will tell you afterward whether the load was complete rather than merely error-free.

Then copy the file itself: `cp db.sqlite3 db.sqlite3.bak`. Do not delete the original until step 7 passes.

## 4. Create the database and role

```bash
psql -U postgres -c "CREATE DATABASE myapp_dev;"
psql -U postgres -c "CREATE USER myapp WITH PASSWORD 'devpassword';"
psql -U postgres -c "ALTER DATABASE myapp_dev OWNER TO myapp;"
psql -U postgres -c "ALTER ROLE myapp CREATEDB;"
```

That last line is not optional if you ever run `manage.py test`. The test runner creates and drops a separate `test_myapp_dev` database, and without `CREATEDB` on the role it fails with a permission error that looks unrelated to your test.

## 5. Point settings at Postgres

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "myapp_dev",
        "USER": "myapp",
        "PASSWORD": os.environ["POSTGRES_PASSWORD"],
        "HOST": "127.0.0.1",
        "PORT": "5432",
    }
}
```

Two details worth getting right. Use `127.0.0.1` rather than `localhost`; on Windows and on some Linux configurations `localhost` resolves to `::1` first, and if Postgres is only listening on IPv4 you get a connection-refused that looks like the server is down. And the engine string is `django.db.backends.postgresql`; the old `postgresql_psycopg2` alias was removed years ago.

Keep the password in an environment variable or whatever mechanism the project already uses, not in the file you commit.

## 6. Build the schema, then load

```bash
python manage.py migrate
python manage.py loaddata dump.json
```

`migrate` has to run first against the empty database. `loaddata` only inserts rows; it does not create tables. The load runs inside a single transaction, so a failure partway through rolls back completely rather than leaving you with a half-populated database to untangle.

## 7. Verify, then clean up

Re-run the count command from step 3 and compare it against the saved output line by line. Then:

```bash
python manage.py migrate --check    # exits 0 if no migrations are pending
python manage.py runserver
```

Log into the admin with an existing account. That single action exercises auth, sessions, permissions, and content types at once, which is most of what could have gone wrong.

Once that passes, delete `dump.json`. It contains password hashes and whatever real data your dev database had. Keep `db.sqlite3.bak` for a week or so.

## Where this usually breaks

**`duplicate key value violates unique constraint "django_content_type_app_label_model_..."`** means contenttypes was not excluded, or `loaddata` ran twice. Recover by dropping and recreating the database (`DROP DATABASE myapp_dev;`), re-running `migrate`, and loading exactly once.

**`Could not load <app>.<Model>(pk=N): null value in column "x" violates not-null constraint`**, or a type error on a date or integer column, is the expected consequence of SQLite not enforcing much. A NULL, an empty string, or a wrong-typed value has been sitting in that column and Postgres is the first thing to object. Fix the offending rows in SQLite (switch settings back temporarily) or hand-edit `dump.json`, then dump and load again. This is the failure mode most likely to cost you time, and how much depends entirely on how old and hand-edited your dev data is.

**A `<table>_pkey` duplicate-key error on the first new record you create after migrating** is a sequence out of sync: Postgres is handing out IDs starting from 1 while your loaded rows already occupy those values. Django resets sequences at the end of a successful `loaddata`, so this only shows up if you loaded per-app or interrupted the load. Fix:

```bash
python manage.py sqlsequencereset myapp | python manage.py dbshell
```

**Third-party or homegrown code that stores content-type IDs in a plain integer column**, rather than as a real FK to `ContentType`, will point at the wrong model afterward, because the new content-type IDs are assigned in migration order and will not match the old ones. Properly declared `GenericForeignKey` fields are fine. I cannot tell you whether you have any of the improper kind without seeing the project.

**`MemoryError` or a load that crawls** means the JSON is too large; `loaddata` parses the entire file into memory. Above a few hundred megabytes, dump per app and load in dependency order, or move the bulk tables with `pgloader` and use Django only for auth. For a dev database this is unlikely.

**A `NotSupportedError` naming the server version** means your Postgres predates what your Django release supports. Each Django version raises that floor, so check your specific version's release notes rather than trusting a number from me.
